Beluga AI v2.13.2 closes out the DX-1 initiative's next two sprints: v2.12.0 added a local dev loop with `beluga run`, `beluga dev`, and `beluga test`, and v2.13.0 introduced `beluga eval` for running structured evaluations against agents from the command line.

## The progression: scaffold, develop, evaluate

v2.11.0 solved the first-fifteen-minutes problem with `beluga init` and `beluga new`. A developer could generate a working project and drop in component stubs, but the workflow after that scaffolding step still relied on ad-hoc `go run` invocations, bespoke test fixtures for deterministic LLM behavior, and evaluation scripts written per-project.

The v2.12.0 and v2.13.0 releases fill in the two gaps immediately downstream of scaffolding. Local iteration and evaluation are now first-class CLI surfaces, on the same footing as project creation. The arc is deliberate: scaffold with `beluga init`, develop against a live or mocked model with `beluga run`/`dev`/`test`, and measure with `beluga eval`.

## What shipped in v2.12.0

### `beluga run` — execute a Beluga program

`beluga run` runs the entry point of a Beluga project against a configured LLM provider, reading credentials and defaults from the project's configuration rather than requiring them on the command line. It is the intended replacement for `go run ./...` when working inside a scaffolded project, because it also wires observability bootstrap before the program starts.

### `beluga dev` — reload loop for iterative development

`beluga dev` watches the project source tree and re-runs the program on file changes. The reload loop is intended for the inner dev cycle where a developer is tuning a prompt, adjusting a tool definition, or iterating on agent behavior and wants each save to produce a fresh run.

### `beluga test` — run tests with a mock LLM

`beluga test` executes the project's Go test suite with the mock LLM capability enabled by default. The mock LLM returns deterministic, scripted responses, which removes the two operational problems with testing agent code against real providers: flakiness from model variation, and cost from test runs hitting paid endpoints.

A typical test sets a scripted response and asserts against the agent's observable behavior rather than the model's exact output:

```go
package agents_test

import (
	"context"
	"testing"

	"github.com/lookatitude/beluga-ai/v2/llm"
	"github.com/lookatitude/beluga-ai/v2/llm/providers/mock"
)

func TestAgentGreeting(t *testing.T) {
	ctx := context.Background()

	// Register the mock provider with a scripted response.
	mock.Register("greeting-test", mock.Script{
		Responses: []string{"Hello from the mock LLM."},
	})

	model, err := llm.New("mock", llm.Config{Profile: "greeting-test"})
	if err != nil {
		t.Fatalf("llm.New: %v", err)
	}

	resp, err := model.Generate(ctx, "Say hello.")
	if err != nil {
		t.Fatalf("Generate: %v", err)
	}

	if resp.Content != "Hello from the mock LLM." {
		t.Fatalf("unexpected response: %q", resp.Content)
	}
}
```

The mock provider is registered through the same LLM registry used by every other provider, so test code and production code resolve models through identical call sites. That symmetry is intentional: the only difference between a unit test and a running program is which provider name is passed to `llm.New`.

### Real observability bootstrap

The observability bootstrap stub from v2.10.0 is now wired. `beluga run` initializes tracing, metrics, and logging exporters from the project's configuration before the program's `main` executes, so traces emitted by agent calls, tool invocations, and the evaluator reach the configured backend without per-project boilerplate.

## What shipped in v2.13.0

### `beluga eval` — run structured evaluations

`beluga eval` executes a named evaluation run against an agent defined in the current project. An evaluation describes the dataset of inputs to exercise, the agent under test, and the judges that score each output. The CLI loads the evaluation definition, runs each case, aggregates the judge verdicts, and reports the results.

```shell
# Run an evaluation defined in the project's eval/ directory.
beluga eval --name customer-support-v1

# Pin the model under test instead of using the project default.
beluga eval --name customer-support-v1 --model anthropic:claude-3-5-sonnet-20241022
```

The eval package that underpins the CLI is scaffolded in this release — the judge interface, the case-runner, and the verdict reporter are in place. Subsequent releases will extend the library with additional judge types and reporting formats; the CLI surface is stable.

This is the connection point with the observability work from v2.12.0. Eval runs emit traces and verdicts through the same bootstrap that wraps `beluga run`, so a CI pipeline can collect eval results in the same telemetry backend as production agent runs without extra wiring.

## v2.13.1 and v2.13.2

v2.13.1 (2026-04-22) incorporated framework-workflow learnings from the DX-1 S4 sprint into the documentation under the contributing section. v2.13.2 (2026-04-22) is a CI maintenance release that refreshed the generated `CODE-QUALITY.md`, `SECURITY.md`, and changelog reports — no user-visible framework changes.

## Breaking changes

None. The v2.12.0 and v2.13.0 CLI additions are new commands and do not alter existing behavior. Projects scaffolded with v2.11.0 can upgrade to v2.13.2 without code changes.

## What's next

The DX-1 initiative continues. With scaffold (`init`/`new`), develop (`run`/`dev`/`test`), and evaluate (`eval`) in place, the next iteration focuses on deepening the eval package: a broader set of built-in judges, structured output formats for CI consumption, and tighter integration between eval verdicts and the tracing pipeline bootstrapped in v2.12.0.

A `beluga doctor` command for diagnosing configuration issues remains on the roadmap for a subsequent sprint.

See the [full changelog](/docs/contributing/project-reports/changelog) for the complete commit list across v2.12.0, v2.13.0, v2.13.1, and v2.13.2. Runnable Beluga examples are maintained at [`lookatitude/beluga-examples`](https://github.com/lookatitude/beluga-examples) and are tested automatically against every new release.
