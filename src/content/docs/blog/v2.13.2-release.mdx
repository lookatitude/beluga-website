Beluga AI v2.13.2 closes out the v2.13.x series with a new CLI entry point, `beluga eval`, that runs evaluation suites against Beluga agents and pipelines directly from the command line.

## Why an eval CLI

Evaluating agent output has been a solvable-but-awkward problem in Beluga since v2.8.0, when the `eval/judge` package shipped with its weighted-rubric scoring and LLM-as-Judge primitives. The package gives you everything needed to grade a model response against a structured rubric, but the ergonomics of actually running a suite — iterating a set of prompts, routing them through an agent, collecting verdicts, and printing a summary — were left to the caller.

That gap mattered less when evaluation was a one-off exercise during model selection. It matters more now that teams are running evaluation as part of their development loop: before a prompt change lands, before a provider swap, before a release. A loop that requires a custom harness for each project puts friction in exactly the place teams wanted to remove it.

`beluga eval` is the standard harness. It treats eval suites as first-class artifacts in a Beluga project, with a predictable directory layout, a consistent invocation pattern, and output formats that slot into CI pipelines without additional glue.

## What shipped across v2.13.x

The v2.13.x series shipped in three tags on April 22nd, with the headline change in v2.13.0 and documentation plus CI follow-ups in the two patch releases.

**v2.13.0** added the `beluga eval` command and the scaffolded eval branch of the CLI. The command registers as a new top-level subcommand on the Cobra root introduced in v2.10.0, alongside `beluga provider`, `beluga version`, `beluga init`, and `beluga new`. It closes LOO-154 and completes the fourth sprint of the DX initiative.

**v2.13.1** updated framework documentation with workflow learnings captured during DX-1 Sprint 4 (C-020 and C-021). No API changes.

**v2.13.2** contains CI and chore updates only. No API changes.

### `beluga eval init` — scaffold an eval directory

Following the pattern established by `beluga init` and `beluga new` in v2.11.0, the eval CLI scaffolds a predictable structure when invoked with the `init` subcommand. Run it from the root of a Beluga project:

```shell
# Inside an existing Beluga project
beluga eval init

# The command writes the eval branch:
# eval/
#   suite.go         # Go entry point that declares suites and rubrics
#   fixtures/        # Prompt fixtures, one file per case
#   rubrics/         # Weighted rubric definitions
```

The generated `suite.go` wires the scaffolded fixtures and rubrics into an `eval/judge` suite definition. You edit the Go file directly to declare additional suites; you add cases by dropping fixture files under `eval/fixtures/`.

### `beluga eval run` — execute a suite

Once a suite is defined, `beluga eval run` loads it, runs every case through the configured agent or model, scores each response with the judge model, and prints a summary. The command exits non-zero if the aggregate score falls below the threshold declared in the suite, which makes it suitable as a step in CI.

```shell
# Run the default suite
beluga eval run

# Run a specific named suite with a custom pass threshold
beluga eval run --suite regression --threshold 0.85

# Emit JSON for downstream processing
beluga eval run --format json
```

## A compilable eval suite

The scaffolded `suite.go` gives you a real starting point. The following example declares a single suite with two cases, scored against a two-criterion rubric. It compiles against v2.13.2 and runs end-to-end once you set the appropriate API key.

```go
package main

import (
	"context"
	"fmt"
	"os"

	"github.com/lookatitude/beluga-ai/v2/config"
	"github.com/lookatitude/beluga-ai/v2/eval/judge"
	"github.com/lookatitude/beluga-ai/v2/llm"
	_ "github.com/lookatitude/beluga-ai/v2/llm/providers/anthropic"
)

func main() {
	ctx := context.Background()

	subject, err := llm.New("anthropic", config.ProviderConfig{
		APIKey: os.Getenv("ANTHROPIC_API_KEY"),
		Model:  "claude-3-5-haiku-20241022",
	})
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	judgeModel, err := llm.New("anthropic", config.ProviderConfig{
		APIKey: os.Getenv("ANTHROPIC_API_KEY"),
		Model:  "claude-3-5-sonnet-20241022",
	})
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	rubric := judge.Rubric{
		Criteria: []judge.Criterion{
			{Name: "accuracy", Weight: 0.7, Description: "Response is factually correct."},
			{Name: "concision", Weight: 0.3, Description: "Response avoids unnecessary verbosity."},
		},
	}

	suite := judge.Suite{
		Name:      "smoke",
		Subject:   subject,
		Judge:     judgeModel,
		Rubric:    rubric,
		Threshold: 0.75,
		Cases: []judge.Case{
			{Name: "capital", Prompt: "What is the capital of France?"},
			{Name: "primes", Prompt: "List the first five prime numbers."},
		},
	}

	report, err := suite.Run(ctx)
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	if !report.Passed {
		fmt.Fprintf(os.Stderr, "suite failed: aggregate %.2f below threshold %.2f\n", report.Aggregate, suite.Threshold)
		os.Exit(1)
	}

	fmt.Printf("suite passed: %.2f\n", report.Aggregate)
}
```

The blank import of `github.com/lookatitude/beluga-ai/v2/llm/providers/anthropic` registers the Anthropic provider with the LLM registry, and `llm.New("anthropic", ...)` resolves it by name. Using two different models for the subject and the judge is the recommended pattern: a smaller model under test, a stronger model grading.

Running `beluga eval run` against a scaffolded project is equivalent to compiling and executing this code, with the CLI handling suite discovery, flag parsing, and output formatting.

## What's next

The CLI now covers the three DX primitives that matter most during day-to-day development: project creation (`beluga init`, `beluga new`), evaluation (`beluga eval`), and inspection (`beluga provider`, `beluga version`). The DX initiative's next sprint turns to `beluga doctor`, a diagnostic command for identifying common configuration issues — missing API keys, stale module paths, misregistered providers — before they surface as runtime errors.

The observability groundwork carried forward from v2.10.0 is also closer to landing. Wiring agent traces and judge verdicts from the `eval/judge` package into a unified telemetry pipeline is the next substantive feature area, and the `beluga eval` harness now provides a natural collection point for those signals.

See the [full changelog](/docs/contributing/project-reports/changelog) for the complete commit list across v2.13.0, v2.13.1, and v2.13.2. Runnable companions to the example above are maintained at [`lookatitude/beluga-examples`](https://github.com/lookatitude/beluga-examples), and the [quickstart](/docs/start) covers installing the `beluga` binary and running your first suite.
