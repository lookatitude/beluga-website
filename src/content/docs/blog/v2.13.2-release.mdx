Beluga AI v2.13.2 closes the DX-1 developer-experience series. Since v2.11.0 the CLI has gained a local dev loop (`beluga run`, `beluga dev`, `beluga test`), a mock LLM provider for offline iteration, an observability bootstrap, and an evaluation command (`beluga eval`). A Beluga developer can now scaffold a project, run it locally without a paid API call, and evaluate it against test cases — all from one binary.

## The arc so far

The DX-1 series targeted the steps between installing Beluga and reaching a running, observable, evaluated agent. The path looked like this:

- **v2.10.0 / v2.10.1** — Cobra-based CLI foundation and the `github.com/lookatitude/beluga-ai/v2` module path fix.
- **v2.11.0** — `beluga init` and `beluga new` for scaffolding projects and components.
- **v2.12.0** — `beluga run`, `beluga dev`, `beluga test`, a mock LLM provider, and an observability bootstrap.
- **v2.13.0** — `beluga eval` for running evaluations against scaffolded test cases.
- **v2.13.1** — internal documentation capturing learnings from the sprint (no user-visible changes).
- **v2.13.2** — CI and housekeeping. This is the tag being announced; it rolls up the user-visible changes from v2.12.0 and v2.13.0.

With v2.13.2 in place, the four phases of a local iteration — scaffold, run, test, evaluate — are all reachable from `beluga <subcommand>`.

## What shipped since v2.11.0

### `beluga run`, `beluga dev`, `beluga test` — the local dev loop (v2.12.0)

`beluga run` executes a scaffolded project against its configured providers. `beluga dev` does the same with a file watcher: edits to `.go` files trigger a rebuild and restart, which matters when a developer is iterating on prompts or tool definitions. `beluga test` runs the project's Go tests with Beluga's default test tags applied, so tests that depend on provider registration see the same environment as `beluga run`.

```shell
# Run the scaffolded project once
beluga run

# Iterate with a file watcher
beluga dev

# Run the Go test suite with Beluga's test tags
beluga test
```

The three commands read configuration from the same `beluga.yaml` that `beluga init` generates, which keeps the surface area small: one config file, one binary, three entry points.

### Mock LLM provider — offline iteration (v2.12.0)

The dev loop is most useful when it does not require a paid API call on every restart. v2.12.0 ships a mock LLM provider registered under the name `mock`. It returns deterministic responses driven by a small config block, which is enough to exercise agent logic, tool-calling branches, and routing without hitting Anthropic, OpenAI, or any other upstream.

Switching to the mock provider is a config change:

```yaml
# beluga.yaml
llm:
  provider: mock
  model: mock-sonnet
  responses:
    - "I will check the weather for Paris."
    - "The current temperature in Paris is 14°C."
```

Swap `provider: mock` back to `provider: anthropic` (or any other registered provider) when you're ready to exercise the real model. The mock provider is not a substitute for evaluation against real models. It exists to make the inner loop free and fast.

### Observability bootstrap (v2.12.0)

Scaffolded projects now start with OpenTelemetry wiring in place. Traces and metrics are emitted to the local OTLP endpoint by default; production users point the OTLP exporter at their own collector. The bootstrap satisfies the stub placed in v2.10.0 and means that `beluga run` produces usable telemetry on the first execution, not after a manual wiring pass.

### `beluga eval` — evaluation CLI (v2.13.0)

`beluga eval` runs a project's evaluation suite. A scaffolded project includes an `eval/` directory with test cases; `beluga eval` executes them, records judge verdicts, and prints a summary. The command is designed to run both locally (during development) and in CI (as a merge gate).

From the shell:

```shell
# Run the full eval suite defined under eval/
beluga eval

# Run a single named suite
beluga eval --suite customer-support

# Emit machine-readable output for CI
beluga eval --format json > eval-results.json
```

The Go integration point is the `eval` package. A minimal programmatic use — for embedding evaluation into a larger test harness rather than invoking the CLI — looks like this:

```go
package main

import (
	"context"
	"fmt"
	"os"

	"github.com/lookatitude/beluga-ai/v2/eval"
)

func main() {
	ctx := context.Background()

	suite, err := eval.LoadSuite("eval/customer-support")
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	report, err := suite.Run(ctx)
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}

	fmt.Printf("passed: %d / %d\n", report.Passed, report.Total)

	if report.Passed < report.Total {
		os.Exit(1)
	}
}
```

`eval.LoadSuite` reads the suite definition from disk. `suite.Run` executes each case against the configured provider and invokes the configured judges. The returned report carries per-case verdicts and aggregate counts. Exit codes propagate to CI runners without additional plumbing.

## Breaking changes

None. v2.12.0, v2.13.0, v2.13.1, and v2.13.2 are additive. Projects scaffolded on v2.11.0 continue to build; upgrading the Beluga module pulls in the new subcommands without requiring code changes.

The module path change from v2.10.1 still applies to anyone upgrading from a pre-v2.10.0 release — the migration note in the [v2.11.0 announcement](/blog/v2.11.0-release) covers the mechanical `sed` rewrite.

## Fixes and chores

v2.13.1 is a documentation-only release capturing internal framework-workflow learnings from the DX-1 S4 sprint. v2.13.2 is CI and housekeeping: no user-visible behavior changes, and it is the tag that consolidates v2.12.0 and v2.13.0 for this announcement.

## What's next

The DX-1 series is complete. The next area of work is the DX-2 series, which focuses on tightening the feedback between `beluga eval` and `beluga dev` — specifically, surfacing judge verdicts inside the dev-loop watcher so that a failing eval case produces the same fast signal as a failing Go test. A `beluga doctor` command for diagnosing common configuration issues is also on the roadmap.

See the [full changelog](/docs/contributing/project-reports/changelog) for the complete commit list across v2.12.0, v2.13.0, v2.13.1, and v2.13.2. Runnable Beluga examples are maintained at [`lookatitude/beluga-examples`](https://github.com/lookatitude/beluga-examples) and are tested automatically against every new release.
